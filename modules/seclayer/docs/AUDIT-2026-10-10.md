# Codebase audit, 2026-10-10

A pre-launch review of seclayer.app: authentication, the SSRF guard, domain-ownership gating, nmap,
the headless browser, payments, the MCP endpoint, secrets at rest, deployment and CI. Every finding
below was reproduced in code before it was changed, and each fix has a test that fails on the old
behaviour. Not read line by line: the red-team and aggressive probe modules, `paramFuzzer`, the
template engine, the queue and lease internals, the account routes and most of the frontend.

## What held up

Sign-in codes (scoped lookup, five attempts, one live code per address, uniform failure message),
Google ID-token verification, the SSRF guard (IPv4 and IPv6 in every notation, DNS pinned at connect
time, redirects re-validated), the browser egress proxy, ownership scoping on scan, report and nmap
routes, the origin lock, the Stripe signature check, hashed session and API-key storage, no
dynamic SQL built from input, and a clean `npm audit` once the lockfile in PR #1 is applied.

## Findings and what was done

| # | Finding | Severity | Status |
|---|---|---|---|
| 1 | Chromium ran `--no-sandbox` as root in the app container with the app's secrets in its environment | High | Fixed. `server/browserLaunch.ts` gives the browser a short environment allow-list; in the image it starts through `scripts/seclayer-chromium.sh`, which drops to `nobody`. Verified in the built image: app uid 0, all browser processes uid 65534, none can see `ENCRYPTION_KEY` or `DATABASE_URL`, pages render. The Dockerfile runs the wrapper with `--version` so a moved binary fails the build. |
| 2 | Domain verification proved a DNS name once, forever; a TXT-verified domain could be pointed at a third party's IP and scanned with nmap | High | Fixed. The proof is re-checked at most daily; nmap requires the well-known file live over HTTPS, at launch and again when the worker runs. Verification routes are rate limited and a user can hold 50 domains. |
| 3 | Scan target credentials (`scans.authHeader`) stored in cleartext and returned in API responses | High | Fixed. Sealed with `ENCRYPTION_KEY` (refuses cleartext in production), opened only for the worker, replaced by `hasAuthHeader` in responses. Existing rows are sealed once at boot. |
| 4 | Stripe credit grant was check-then-grant, with no unique constraint; no refund or delayed-payment handling | Medium | Fixed. One transaction (user row locked on Postgres), a unique index created at boot as a backstop, `async_payment_succeeded` grants, a full refund or a dispute reverses once. Verified with 8 concurrent deliveries on real Postgres. |
| 5 | MCP scan had no per-user in-flight cap, so one key could hold every scan slot | Medium | Fixed. Same cap as the dashboard; refuses with 429 before a credit is taken. |
| 6 | MCP scan was synchronous, so a scan past Cloudflare's ~100 s cutoff returned 524 while still running and spending the credit | Medium | Fixed. After 80 s (`MCP_SYNC_WAIT_MS`) it answers 202 with `scanId` and `pollUrl`; the scan finishes in the background, and a failure after that is still refunded. `@seclayer/mcp` waits out a 202. |
| 7 | Production did not check `ENCRYPTION_KEY` or `ORIGIN_AUTH_SECRET` at boot | Medium | Fixed. A missing or malformed `ENCRYPTION_KEY` refuses to boot; a missing `ORIGIN_AUTH_SECRET` logs that the origin lock is off. |
| 8 | "Cancelling an nmap scan only kills the process on the replica that handled the cancel" | n/a | **Not a defect: the audit was wrong.** `nmapWorker.ts` already polls for a cancellation made on another replica (`watchForCancel`) and kills its own process. No change. |
| 9 | Malformed JSON and oversized bodies returned 500 | Low | Fixed. 400 and 413, with a fixed message. |
| 10 | MCP read endpoints accepted the API key in the query string (logged by every proxy) | Low | Fixed. Header only; a query key is refused with the reason and a rotate-the-key notice. |
| 11 | Autofix path check was lexical, so a symlink in the repo could escape it | Low | Fixed. Read, list and edit resolve the real path and refuse anything outside the repo. |
| 12 | nmap targets resolved with raw c-ares; verification routes had no rate limiter | Low | Fixed. Shared resolver; limiter added (see 2). |
| 13 | CI had no dependency audit, secret scan or Docker build, and built every PR twice | Low | Fixed. Three jobs added; pushes run only on `main`. |
| 14 | Stale text: "magic link" sign-in, "nothing applies the Postgres schema at runtime" | Low | Fixed. |

## Still open, by decision rather than oversight

- The container still runs the app as root, because nmap needs raw sockets. The browser no longer
  shares that privilege; the app process itself does.
- The browser still runs without Chromium's own sandbox. A managed container cannot grant the user
  namespaces it needs. The unprivileged user and the empty environment are what limit it.
- A partial Stripe refund is deliberately not reversed (there is no sensible fraction of a credit
  pack); a person settles it by hand.
- Operational items from the readiness notes are unchanged: no grade for scans blocked by bot
  protection, cookie findings that vary between runs, scans running inside the web process, Stripe
  and `HEALTH_DETAIL_TOKEN` unset.

## Before enabling payments

Set the Stripe webhook to deliver `checkout.session.completed`, `checkout.session.async_payment_succeeded`,
`charge.refunded` and `charge.dispute.created`, and check the boot log for the unique-index message.
